# Conversor de Partituras — contexto para o Claude

**Atualizado em 18/11/2026, horário de Campo Grande (UTC−4).** Repositório `score-to-musicxml`. O aplicativo web, iOS e Android transforma PDFs, imagens e fotos de partituras em MusicXML para músicos, professores e estudantes. O usuário pode conferir a conversão, ouvir a partitura com acompanhamento visual e abrir o arquivo em editores como MuseScore. Administradores gerenciam usuários, acesso e auditoria.

## Fluxos do produto

- **Entrada e biblioteca.** O usuário entra com a conta, escolhe melodia, piano, violão solo ou duo de violões e envia PDF ou imagem. No mobile pode escolher arquivo, galeria ou câmera, e o iOS tem scanner nativo de documentos com várias páginas. O app trata cancelamento e permissão negada. Web e mobile oferecem lista, favoritos, renomeação, seleção e ações em lote, lixeira e restauração. Configurações reúne perfil, idioma, ajuda, privacidade e compras. O guia opcional de quatro etapas aparece na primeira abertura e pode ser revisto em **Conhecer o app**. Há textos em PT/EN.
- **Conversão e cobertura.** A API valida assinatura do arquivo, tamanho e permissão, grava o original em storage privado, cria a tentativa e registra o uso na mesma transação. O reconhecimento óptico de música (OMR) roda por página. Capas e páginas em branco são tratadas no pipeline. O resultado parcial admite lacunas de páginas inteiras com aviso. Perder uma pauta de piano ou uma parte obrigatória dentro de uma página reprova a tentativa. Uma falha transitória admite uma retentativa automática e há uma manual por envio, sem novo débito. Estouro do orçamento global não dispara uma segunda conversão inteira automaticamente. Uma falha posterior preserva a saída anterior. Cobertura informa o que foi processado. Fidelidade exige comparar eventos, símbolos e estrutura com a fonte.
- **Entrega e conferência.** O resultado selecionado é entregue automaticamente. **Conferir** compara original e convertido, explica avisos e localiza trechos. Quando existem propostas fundamentadas de nota ou pausa, é possível aceitar, rejeitar ou desfazer. Quando faltam propostas, a comparação continua disponível e a tela explica o estado. **Voltar à partitura** retoma a leitura e **Fechar** encerra os detalhes. O histórico abre e exporta versões antigas em leitura, preservando a atual. Na branch, um documento com várias páginas pode mostrar a primeira página reconhecida, provisória, enquanto as outras processam. Essa prévia não libera áudio ou download final e é retirada ao concluir, falhar ou mudar de tentativa.
- **Leitor e exportações.** O MusicXML preserva a notação editável. O MIDI é derivado sob demanda, sem arquivo MIDI persistido no servidor. O leitor oferece destaque de notas, acordes e pausas, acompanhamento por página, posição, ajuste de andamento e repetição entre compassos. O piano é o timbre padrão e o andamento de fallback é 70 BPM. A política atual permite ouvir as páginas convertidas de um parcial quando o XML permite reprodução, com aviso sobre as lacunas. Exportação MIDI exige resultado completo com cobertura e validação próprias. Algumas seções antigas do README e do contrato descrevem os bloqueios que existiam antes da restauração da escuta de 08/10.
- **Conta e plano.** O backend aplica autorização de proprietário ou administrador aos arquivos, inclusive prévia, evidências e downloads. O limite padrão do plano gratuito é de três conversões, configurado por `FREE_SCAN_LIMIT`. `premium_unlock` é uma compra não consumível vinculada à conta, com restauração e validação pelo backend. O administrador pode conceder e revogar acesso e consultar usuários e auditoria. Retentativa do mesmo envio não consome nova conversão.

Comandos para preparação de ambiente novo em Node 22, como na CI. Em checkout já preparado, reutilize dependências, banco de desenvolvimento e caches. Use o `.env` existente quando apropriado. Evite seed em um banco cujo conteúdo precise ser preservado.

```sh
# Em ambiente novo, preparar .env a partir de .env.example.
npm ci
docker compose up -d postgres redis
npm run db:generate
npm run db:migrate
npm run db:seed
npm run dev
```

`npm run dev` sobe API (4000), web (5173) e worker. `npm run dev:mobile` abre o Expo para desenvolvimento. Para regressão, use `npm run lint`, `npm run build`, `npm test` e `node --test --test-concurrency=2 scripts/tests/*.test.mjs`. Para focar um workspace, por exemplo, `npm run test -w apps/mobile`. A integração PostgreSQL usa `SCORE_PRISMA_INTEGRATION=1` e o banco QA descartável exigido pela suíte em `apps/api/src/tests/prismaConversion.integration.test.ts`. A CI valida build e testes em Node 22, regressões dos scripts e APK Android Debug com Java 17.

Variáveis a revisar por ambiente: `DATABASE_URL`, `REDIS_URL`, `SESSION_SECRET`, `STORAGE_DIR`, `MAX_UPLOAD_BYTES`, `OMR_ENGINE`, `AUDIVERIS_BIN`, `OMR_MAX_PAGES`, `OMR_CONVERSION_TIMEOUT_MS`, `SOURCE_VISUAL_READER_BIN`, `API_DOMAIN`, `WEB_DOMAIN`, `WEB_ORIGIN`, `VITE_API_URL`, `EXPO_PUBLIC_API_URL`, `EXPO_PUBLIC_PLAYER_URL`, `APPLE_IAP_*` e `GOOGLE_PLAY_*`. ## Como preparar uma atualização de produção

1. **Antes de publicar.** Fixar o commit candidato, registrar o que está ativo em cada serviço e comparar as migrations. Confirmar backups privados do PostgreSQL, do storage e dos artefatos anteriores, com recuperação ensaiada. Em homologação, validar compatibilidade com resultados antigos, histórico, quotas e compras. Nunca usar o banco de produção para a suíte de integração.
2. **Servidor e web.** A pilha Docker Compose do repositório reúne PostgreSQL, Redis, API, worker, web (Nginx) e Caddy para HTTPS. O registro de 09/11 mostra que o Nginx ativo no host servia os arquivos web de `/var/www/converter/apps/web/dist`. Antes de um deploy, confira o serviço que realmente atende o domínio e o diretório servido. O comando da pilha Compose é `npm run deploy:prod` no host, com `.env.production` regular e permissão 600. O script valida o ambiente e os domínios, compila, valida o Caddy, sobe os serviços e verifica readiness. O entrypoint executa a guarda das compras Apple e `prisma migrate deploy`; o deploy só roda o seed idempotente depois do readiness. O procedimento de promoção controlada do runbook prevê API/worker antes da web, validando cada etapa. `npm run deploy:vps` é a alternativa documentada para uma instalação já configurada com PM2, não para o alvo Docker registrado.
3. **Depois do deploy.** Verificar `/health` e `/ready` (banco, Redis e heartbeat do worker), além de login, lista, partitura já convertida, histórico quando aplicável, downloads MusicXML/MIDI e `/mobile/player/`. Rodar uma conversão real controlada e conferir tentativa, cobertura, preview e exportações. Readiness sozinho não exercita OMR. Em incidente, restaurar a imagem ou os assets anteriores e testar novamente. Preservar as migrations aditivas e os exports antigos. Os registros históricos de publicação descrevem backups e reversões pontuais de HTML/artefatos.
4. **iOS físico e App Store.** Toda instalação física passa por `scripts/install-ios-device-release.sh`, conforme `AGENTS.md`. Use Xcode/CocoaPods e a assinatura e o perfil existentes. Configure `EXPO_PUBLIC_API_URL=https://converter.nossateoria.com.br` e `EXPO_PUBLIC_PLAYER_URL=https://converter.nossateoria.com.br/mobile/player` no ambiente do build. Para o aparelho, o procedimento comprovado usou `xcodebuild -workspace apps/mobile/ios/ScoretoMusicXML.xcworkspace -scheme ScoretoMusicXML -configuration Release -sdk iphoneos -destination 'generic/platform=iOS' -derivedDataPath apps/mobile/ios/build CURRENT_PROJECT_VERSION=<BUILD> build`. Substitua `<BUILD>` pelo número escolhido. Execute `bash scripts/install-ios-device-release.sh "<caminho-do-app>" "<UDID-do-iPhone>" "<build-esperado>"`. O script exige `main.jsbundle`, rejeita artefatos Debug, valida bundle ID `com.scoretomusicxml.app`, número e assinatura, instala e lê a versão de volta. Verifique que o app abre pelo ícone sem Metro ou conexão com o Mac. Para a loja, arquive em Release, exporte o IPA App Store, confira versão, assinatura e assets do leitor. Se houver pacote de teste do mesmo archive, compare o hash do JavaScript. Em uma rodada autorizada, confirme processamento do build, selecione-o na versão 1.0, reconcilie a nota, verifique a conta de revisão, vincule `premium_unlock` ao mesmo envio e confirme lançamento manual. Upload, submissão, aprovação e lançamento são etapas distintas.
5. **Android.** Consulte o próximo código disponível no Play Console e a credencial de upload existente. Rode `npm run release:preflight -w apps/mobile`. A partir de `apps/mobile`, use `eas build --platform android --profile production` para gerar o AAB assinado. Repita o preflight com `ANDROID_UPLOAD_CERT_SHA256`, `--aab` e `--merged-manifest`. Valide primeiro na faixa interna, incluindo RTDN e restauração Google, e só então promova pelas faixas autorizadas. Em falha, pause a expansão e prepare um novo artefato mantendo a API compatível.
6. **Recursos de validação.** Antes de compilar ou testar, liste os simuladores com `xcrun simctl list devices` e confirme se estão em uso. Reutilize `apps/mobile/ios/build` para Release e `apps/mobile/ios/build/splash-validation` para Debug simulado, mantendo as configurações e as compilações simultâneas isoladas. A rodada de novembro usou `ScoretoMusicXML iPad` (`A4829934-8239-4D05-A0E4-22683C131599`) e `ScoretoMusicXML iPhone` (`7E0767E5-C851-46C9-9FF7-53BB79B149AE`), ambos iOS 27.0, para a cobertura visual. Conserve simuladores, dados e caches em uso. Registre o UDID e o caminho efetivamente usado em cada validação.
